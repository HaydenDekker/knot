## Deviations
- **In-cycle settle added (not in the plan text).** The plan's cascade closes the strand channel immediately after the single execution; the file watcher (50 ms poll) delivers in-cycle file events — a dispatched consumer event, the agent modifying its own strand — with a delay, so a dispatch that lands in that window is silently lost instead of flushed at shutdown. The acceptance test `step_captures_dispatched_events_without_executing` requires the dispatch to be captured deterministically, so `step_knot` now waits a bounded settle (`max(5× debounce window, 250 ms)` — 250 ms in tests, 500 ms in production) between the execution and the shutdown cascade. Verified by disabling the settle: the test passes on a fast dev machine (the post-dispatch git-commit tail happens to cover the watcher poll) but the guarantee is timing-dependent without the settle.
- **`print_queued_events` moved from stdout to stderr.** The committed Phase 3 code printed the queue listing with `println!` on the unknown/ambiguous `--event` error path; the plan's acceptance test requires the listing on stderr (it is error-path output, matching the rest of `main.rs` which uses `eprintln!` for errors).

## Discoveries
- **A bare `rig/` directory is not discoverable in step mode.** Rig discovery matches `*-rig` directories; the bare `rig/` name is only the *service* default (created implicitly when zero `*-rig` dirs exist). Step mode has no default fallback at all — zero matches is an error. Binary-level tests therefore use `dev-rig`; this is exactly the "stricter than the service" resolution the plan calls for.
- **Dispatched events are captured with kind `Modified`, not `Created`.** `FileSystemEventDispatcher` creates event files atomically (temp file + rename), so the watcher sees both `Created` and `Modified` for the final path; the debounce window coalesces per `(path, loom, knot)` and keeps the last one. Both kinds are valid captures — the test accepts either.
- **Every step invocation takes ≥ 5 s.** The state-writer task runs forever, so the 5-second JoinSet drain always times out and aborts it (same as the service's Ctrl+C path). The empty-queue "prompt exit" is asserted as `< 30 s`. If step latency becomes a problem, the state writer could take a stop signal — follow-up, out of scope.
- **Pre-seeding the queue in tests is deterministic and watcher-free.** Writing `PendingEvent` JSON files directly to `tie-offs/<rig>/events/<id>.json` before the step works because the disk is the queue and `load_persisted()` runs at step startup; the ID prefix controls FIFO order (filename sort). No debounce wait is needed to build the fixture.
- **The state-writer's 5 s tick lands inside the step's 5 s drain**, so the final `state.json` write reliably captures the post-step queue (the processed head removed, the remainder listed) — `step_writes_state_json` relies on that.
- **`step` early-error paths (unknown event) skip the shutdown cascade.** `step_knot` returns `Err` before dropping the context; the `JoinSet` drop aborts the pipeline tasks and `LoomStopped` is not written. Accepted — the brackets are unbalanced only on error exits, mirroring the service's startup-failure behaviour.

## Notes
- Lib-level tests run `step_knot` on a dedicated thread with its own multi-threaded tokio runtime (mirrors `helpers::start_knot_with_config`, minus the abort handle — `step_knot` is finite); a 120 s `recv_timeout` guards against hangs. Binary-level tests follow the `tests/rig_cli.rs` pattern with `KNOT_TEST_DEBOUNCE_MS=20` / `KNOT_TEST_CHECK_MS=2` on the child process.
- The mock `pi` records one line per invocation (tagged with the `@<strand-path>` argument) in a per-fixture runs log — "exactly one agent run" is asserted against that file, and the echoed strand name distinguishes which event ran (tie-off content is append-per-knot, so both head and second events would land in the same `tie-off-review.md`).
- The dispatch fixture uses a real producer→consumer pair: `planning-loom/plan-creator` (`strand-dir: "./strands"`) and `validation-loom/gap-assessor` (`strand-dir: "event:plan-creator:PlanCreated"`); the producer's mock tie-off carries one `PlanCreated` event block, so event enforcement passes (agent runs exactly once) and the dispatch writes `tie-offs/rig/validation-loom/PlanCreated/event-*.md` mid-step.
