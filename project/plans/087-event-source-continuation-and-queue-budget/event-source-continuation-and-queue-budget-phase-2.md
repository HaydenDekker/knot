## Deviations

- **Budget-exhaustion suppression is a *new* handoff-time check, not just the caps reorder.** The plan's "reorder suppression" names the caps as the existing suppression; the *exhausted-budget* suppression did not exist at handoff (budget exhaustion was only handled at dequeue, as a degenerate deferral). This phase adds the handoff-time check (`stamped_budget < MIN_REMAINING_SECS`) so a continuation that could only be degenerate-deferred on its next hop is suppressed up front — recording `BatchIncomplete (reason: deadline)` instead of writing a dead continuation file. This is required to make the "or an exhausted budget" clause of the checklist testable and to keep the file/commit honest.
- **`dispatch_self_continuation` gained a matching budget backstop** (in addition to the existing caps check) so it never writes a continuation that would be suppressed. It is a pure backstop on the `handle_success` path (the pre-check skips the call on suppression, so it never double-records `BatchIncomplete`), and it makes the function correct when called directly (e.g. the Phase-1 delivery tests).
- **The `[task-loop] handoff` *service-log line* suppression is enforced by the same gate as the loom event** (both sit inside the `else` branch of the suppression pre-check), but is **not directly asserted** in the test: `log_strand_event` writes to stderr via `eprintln!`, which the test harness does not capture. The test asserts the observable loom-event effect (no `TasksIncomplete`, a `BatchIncomplete` instead), which is the same code path that gates the line. The line's suppression follows from the shared gate.

## Discoveries

- The **project vs rig repo split** (the D3 "replay = navigate the project's commits" source) is exactly: the runtime tree lives under `tie-offs/<rig-basename>/` at the **project** root (`derive_runtime_root(rig_dir) = project_root/tie-offs/<rig-basename>`), while the rig's own dir is `project_root/<rig-basename>`. The `FileSystemGitVersioner` commits at `repo_root` with `git add -A` + `git reset -q -- <rig-dir>`, so the runtime tree (tie-offs, event dispatch dirs, the continuation file) is **captured** and the rig source dir is **excluded**. The `commit_capture_tests` seam exercises this with a real `FileSystemGitVersioner` + a real project git repo: a new rig source file (untracked, created after the baseline commit) is staged by `git add -A` and removed by `git reset -q -- rig`, proving the `unstage_rig` exclusion while the continuation file under `tie-offs/` lands in the same commit.
- The **cap test** uses a continuation strand stamped `continuations: 10` (`MAX_CONTINUATIONS`) with a generous `budget-secs: 1200` so the *cap* — not the budget — is the suppression reason; the **budget test** uses a fresh dispatch with a 3s profile timeout (below `MIN_REMAINING_SECS` = 5s) so the stamped budget (`3 − execution_secs`) is deterministically `< 5`. Both assert the suppressed hop records `BatchIncomplete` and emits **no** `LoomEvent::TasksIncomplete`.
- The `suppressed_reason` pre-check short-circuits (caps before budget), so a hop that hits both is reported as `caps` — the iteration cap is the more actionable bound. The two conditions are independent on the normal path.

## Notes

- **Order / commit (D3):** the continuation file is written to disk **before** the per-turn commit. In `handle_success` the self-continuation dispatch runs at `~525`, the late removal at `~770`, and the git commit at `~772`. The commit therefore captures the continuation as a durable artifact.
- **The project `git_versioner` commit captures the continuation; the rig repo stays source-only.** The project commit (`git add -A` at `repo_root`, then `git reset -q -- rig/`) **captures** the continuation: the event dispatch dir `tie-offs/<rig>/<loom>/<event-id>/` is inside the project repo by construction (it is under the project's `tie-offs/` tree, not under the rig dir), and the knot's strand dir — a project path — in the filesystem case. The rig's own git repo (plan 068) is **source-only** (looms, knots, profiles, config) and is excluded from the project commit by `git reset -q -- rig/`; it never contains runtime artifacts. So *replay = navigate the project's commits*: the continuation file + the stamped queue entry appear in the commit, and a reviewer can step through the batch hop by hop.
- **Observability fix (this phase):** today, for an event-source knot the code recorded `LoomEvent::TasksIncomplete` (`continuations: incoming+1`) **and** wrote the `[task-loop] handoff …` service-log line **before** calling `dispatch_self_continuation`, which (pre-Phase-1) returned `Ok(None)`. The log/event thus *claimed* a handoff that never materialized into a file. Phase 1 made the delivery succeed (the claim became true for the unsuppressed path); this phase makes the claim honest in the *suppressed* case too — on cap/budget-exhaustion the event/line are now suppressed with the file, and a `BatchIncomplete` is recorded instead. The log never claims a hop that did not happen.
