## Deviations

- **FIFO test (#10) was the only genuinely-missing row.** The other nine rows were already present (red-first in Phases 0–2). This phase added `continuation_written_to_inbox_is_queued_after_already_queued_events`. It lives in `process_strand_helpers.rs` — not `disk_event_queue.rs` — because the row names *the continuation* specifically: it calls the real `dispatch_self_continuation` to write the file into the event inbox, then the real `DiskBackedEventQueue`. A queue-only test (`disk_event_queue.rs`) would prove generic FIFO but not that a *continuation* takes the append-to-end path.
- **The FIFO test drives the real watcher→debounce contract without spinning the debounce engine.** The debounce's only effect on the queue is `event.into()` (`StrandEvent` → `PendingEvent`, a fresh `generate_event_id()` timestamp) + `push_or_replace` (`src/application/debounce.rs`). The test reproduces exactly that: it converts the continuation's `StrandEvent::Created` via the real `From<StrandEvent>` and calls `push_or_replace`, then asserts `front()` is still the oldest already-queued event and the continuation pops **last**. No async debounce loop is needed.
- **The already-queued events use fixed past 13-digit timestamp prefixes** (`1000000000000-aaaa`, `1500000000000-bbbb`). The queue orders by *filename* (lexicographic), and the continuation's id is a real current Unix-millisecond timestamp (~1.7e12, 13 digits). Short 4-digit prefixes (`1000`/`2000`) would sort *around* a 13-digit `1754…` id and place the continuation mid-queue (the first red run caught this). 13-digit past prefixes (`1000…`, `1500…`) are lexically before any 2026 timestamp, so the ordering is deterministic for the life of Unix-ms.
- **Cap test (#5) switched from a filesystem knot to an event-source knot** to make the "no continuation file" assertion meaningful. The pre-existing cap test used `build_knot_with_profile` (a filesystem knot with the relative `strands` dir, resolved against the test cwd — fragile and shared across tests). Now the knot is an event-source knot, so the inbox is the deterministic absolute path `derive_runtime_root(rig_dir)/test-loom/SomeEvent`; the test asserts that dir holds no `-continuation.md`. The `BatchIncomplete (caps)` / no-`TasksIncomplete` assertions are unchanged (knot source is orthogonal to the cap path).

## Notes
- `execution_secs` is wall-clock (dequeue → handoff) — total processing time including Knot overhead; the stamping tests (`stamp_continuation_budget_*`) fix a known dequeue→handoff span (via `dequeue = now`) and assert the stamped `budget-secs` decays by exactly that span.
- The queue-wait-exemption test is the discriminating one: `continuation_budget_secs_applied_directly_as_runner_timeout` shows the continuation's runner timeout equals the stored `budget-secs` (1200s) even though the `batch-start-epoch` is 24h in the past (queue wait is never folded in).
- The **shared-event-id cross-fire** edge (two knots on the same `(loom, event-id)` would both re-trigger) remains a locked v1 acceptance (documented in the plan's *Risks*); it is not exercised by a test because it is a property of the existing watcher/dispatch fan-out, already covered by `dispatch_fan_out_two_consumers_same_event`, and no such rig shape exists in this repo (checked against the rig).
